# Rubrics — Best-Practices Baseline and Policy Profiles

Rubric A is universal: every skill, any profile, is scored against it. Profiles replace a one-size charter: a skill is scored against the profile **it declares** (frontmatter `metadata.profile`, inherited from its pack), never against a stricter one it didn't claim.

- **name** — ≤64 chars, lowercase letters/digits/hyphens only, no leading/trailing/consecutive hyphens, no XML tags, no reserved words ("claude", "anthropic"); folder name matches the frontmatter `name` exactly
- **description** — ≤1024 chars, non-empty, no XML tags, third person, states WHAT it does and WHEN to trigger with the words a user would actually say; lean pushy (skills under-trigger); all when-to-use lives here, not in the body. **Listing cap** *(added 2026-09-28, code.claude.com/docs/en/skills)*: Claude Code truncates the skill listing at 1,536 characters of `description` plus `when_to_use` combined, so the key use case goes first; the description triggers and does not summarise the workflow (`description-crafting.md`)
- **frontmatter shape** *(verified 2026-08-17; Claude Code key list re-verified 2026-10-01, code.claude.com/docs/en/skills)* — claude.ai uploads, the Skills API, and `package_skill.py` accept exactly six keys: `name`, `description`, `license`, `compatibility` (≤500 chars), `metadata`, `allowed-tools`; every other key — the live page lists fourteen: `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `disallowed-tools`, `model`, `effort`, `context`, `agent`, `background`, `hooks`, `paths`, `shell` — is a Claude Code-only extension and fails those paths with a hard "Unexpected key(s)" error. `allowed-tools` is a per-turn permission **grant** — the listed tools run without asking, every other tool stays callable — never a restriction, so the minimal grant is none unless a step needs a no-prompt tool; `disallowed-tools` exists in Claude Code only. Quote version strings in `metadata` (`version: "1.0"`), as the spec's own example does. **`metadata` is string-only** *(added 2026-10-08, owner decision M3)*: the spec defines `metadata` as "A map from string keys to string values", so every value is a string — quote a number, boolean, null or date — and a nested list or map under `metadata` is a P1 frontmatter defect that a strict parser or upload may reject. Structured data goes in a file beside SKILL.md, as the volatile list does in `volatile.json`; this pack's `build.py` fails the nested form. The Help Center article still shows a 200-char description cap and a `dependencies:` key; the spec and the platform docs govern
- **discoverability test** — from name + description alone, ten realistic requests route correctly; routing is set at this level, not in the body
- **body size** — SKILL.md under 500 lines and under 5,000 tokens (target 2,000–4,000); a reference file every entry point reads counts toward it; move material to reference files past ~300 lines; the context window is a public good. Over 5,000 needs a stated reason in the budget row (Split or keep, below)
- **progressive disclosure** — reference links one level deep; reference files longer than ~100 lines carry a table of contents (Anthropic's published threshold; the pack's former ~150-line house variance is retired 2026-09-27); one reference file per mutually exclusive context, named for its content; each pointer says when to read the file
- **instruction style** — explain-the-why over CAPS imperatives; reserve MUST/NEVER for genuinely fragile steps; match instruction freedom to task fragility; one term per concept throughout
- **feedback loops** *(added 2026-09-28, best practices "Implement feedback loops")* — a quality-critical step carries a validate step and a fix-and-recheck loop (plan, validate, execute), with an intermediate output a check can read; `build-templates.md` has the pattern
- **MCP tool names** *(added 2026-09-28, best practices)* — a skill that calls MCP tools names them fully qualified (`Server:tool_name`), so the tool resolves when several servers are loaded
- **no rot** — no time-sensitive facts hard-coded outside a stamped volatile file; no Windows-style paths
- **dependencies declared** — every tool, script, package, or sibling skill named in the frontmatter `compatibility` field (one line, ≤500 chars: what it needs, what it writes, and the behavior when each is absent) and, where more detail helps, in the body or README; scripts state whether they are run or read. One rule for every profile (2026-10-01, foundation audit PK-8): `compatibility` is the declaration, the body may expand it, never replace it
- **evals exist** — a way to tell the skill worked: trigger evals plus an assertion suite, or a stated reason neither applies
- **model tiers checked** *(added 2026-09-28, best-practices checklist "Tested with Haiku, Sonnet, and Opus")* — the self-audit states which model tiers the skill was checked on; a standard-profile build runs its trigger table on the smallest tier it will be deployed to. An unstated tier list scores this dimension at 5 at most
- **security** — every bundled file audited; what this dimension actually looks for, and the severity each finding files at, is stated once under **Security classes** below (S-1 to S-5), the contract check included
- **invocation control** *(added 2026-08-15, audit finding `rubric-has-no-invocation-control-dimension`)* — a skill whose steps write, commit, push, send, or spend declares `disable-model-invocation: true`, or states in one line, in the skill itself, why model invocation is required (a production runner that fires it through the model is the canonical reason). Files under S-3 when the capability is both side-effectful and silently model-invocable with neither the flag nor the stated reason. `disable-model-invocation` is a Claude Code-only key (**frontmatter shape**, above), so a skill that also ships to claude.ai or the API takes the stated-reason path

## Research reading

*(Added 2026-09-28, observation #0133.)* Build step 3, Audit step 2 and Entry — Refresh read sources the same way. Read the raw Markdown where the host serves it (a `.md` URL, `raw.githubusercontent.com`) rather than a summarising fetch. Record something as **absent** only after an exact-match search of the raw text for the words that would state it. A summariser's "not found" is recorded as **unverified**, never as absent: a summary can drop the one line that matters, and an absence recorded from it rewrites doctrine on a false premise.

## Scoring anchors

1–10 per dimension, overall = average to one decimal. **1–3** absent or broken · **4–6** present but drifts — output or triggering varies · **7–8** ship-ready, minor tweaks · **9–10** consistently correct as-is. Anchor to the skill's real job: a missing TOC on a 40-line reference is a non-issue; on a 300-line one it's a real defect.

## The universal rule

**No undeclared dependencies.** Profiles differ in what a skill may depend on; none permit hiding it. A skill that quietly assumes a tool, a sibling, or an installed package fails its profile — whichever profile that is.

## Parity verdict — best of breed

*(Added 2026-09-26, task-observer observation #0190 and the user's decision of the same day; it replaces the earlier niche verdict — CHANGELOG 1.5.0.)* A skill is built, and judged at every audit, as best of breed on its core job. Build step 4 and Audit step 4 apply this section; the member's body carries only the verdict's shape.

**The verdict's four parts.**

1. **Parity table.** The core job's capabilities, one line each, across the two or three strongest incumbents the scan found — skills, plugins, MCP servers, prompt libraries, dedicated tools. Each line is marked *met* (matches the best incumbent), *beaten* (does it better, and says how), or *out of scope* (with the reason — a boundary the description states, never "not reached yet").
2. **Margin.** At least one named capability no incumbent has, stated so a test can check it. A quality adjective ("cleaner", "more thorough") is not a margin.
3. **Iterate.** For each parity line, research the alternatives and propose at least one way to do it better than the incumbents do. The proposals are the build's improvement list and the audit's next-version list: a skill that only matches the field is a copy of it.
4. **Retire condition.** Stated at build, in the parity register: which incumbent move would erase the margin. At audit, when an incumbent matches every parity line and no margin survives the iterate pass, the audit recommends adopting the incumbent and retiring the member.

A scan that finds no incumbent after checking every source is a finding, recorded with its date: the parity table is empty, the whole job is the margin, and the retire condition names the first kind of incumbent that would count.

**Verdicts.** **PARITY + MARGIN** — every line met, beaten or out of scope, and at least one margin: build (at audit, keep). **GAPS** — a line unmet or no margin yet: the iterate proposals are the plan to close them, and the user decides whether to build now or iterate first. **OVERTAKEN** — part 4's retire condition has fired. Every verdict is information, not a veto; the user decides. A verdict never steers the user to an easier neighbouring job; it says how to win the job asked for.

**A no-go names the rival to use** *(added 2026-09-28, owner decision)*. When the verdict is no-go because a rival already does the whole job — OVERTAKEN, or every line met with no margin surviving the iterate pass — the verdict (and any run card or report carrying it) recommends that rival **by name** and says in plain words how the user would use it in their own work and projects: the install path (the command, marketplace entry or download, as the rival's own docs state it), where it fits in their setup, and what it replaces (the member to retire, or the build that no longer needs doing). "A strong incumbent exists" with no name and no install path is not a finished verdict.

**Two scoping rules.**

- **Adopt tools, never rebuild them.** Runtime infrastructure — an MCP server, a CLI, an API — is used, not reimplemented. Its parity line reads *drives the tool as well as the best skill that drives it*, and the member declares the tool under the universal rule.
- **Split the work.** A job a sibling in the same pack, or in a registered sibling pack, already owns stays with that sibling. It becomes a boundary sentence and a routing seam, not a parity line and not a gap: that is routing, not thinness.

**The parity register.** Each member records its incumbent scan in its own `SOURCES.md`, under a `## Parity register` heading: each incumbent with its link and the date it was checked, the parity table, the margins (each naming its eval case), the iterate proposals, and the retire condition. The register is a volatile surface, because incumbents move: declare it `class: calendar`, `cadence_days: 90` in `volatile.json`, with a `Last verified: <date>` stamp in the file's first lines, where upkeep reads it. Parity detail lives there and not in the member's body — the body names the verdict and points at the register, and the member's registry body budget still binds.

**A test per claim.** Every *beaten* line and every margin ships with an eval case the incumbent's approach would fail: the Input is chosen so that doing the job the incumbent's way produces a checkable miss. A claim with no case is marketing. At audit it is a **P1** finding naming the missing case, and the claim leaves the README until the case exists.

**Ideas, not text.** Techniques can be borrowed; an incumbent's text or code is never copied. Anything adapted is licence-checked and cited in `SOURCES.md`. At audit, copied text or code is a **P0** finding; an adaptation missing its citation or its licence check is **P1**.

**Stay current.** Every audit re-verifies Rubric A's baseline live and re-runs the incumbent scan, whatever the stamps say, and the register's stamp moves only for what the scan actually checked. Where search is unavailable, the audit says the scan was skipped and scores parity against the register as it stands, flagged stale — the same fallback Build step 3 uses for the baseline.

## Parity verdict — partition by reach

*(Added 2026-09-13, observation #0059.)* "Should we build a skill for this?" reads as one question and is two: whether the content is worth writing down at all, and which container should hold it — a skill, a repo's `CLAUDE.md`, project instructions, a handbook page, a CI check. A verdict answering only the first carries an unstated answer to the second, and the unstated answer drives the whole recommendation.

Three axes decide the container, and the partition follows them:

- **Load moment.** A repo's `CLAUDE.md` loads in every session in that repo, unconditionally; a skill loads when its description matches. For a rule that must never be missed while working in one repo, the unconditional load is strictly better.
- **Reach.** A `CLAUDE.md` reaches one repo; a skill reaches every project the rig ever touches. For a rule that will be just as true in the next project of the same class, the skill is the only container that gets it there.
- **Drift surface.** Two containers holding the same rule is a second copy, and it will drift — which is the argument a `do-not-build` usually rests on. Two containers holding **disjoint** rules, each saying in its own text that it does not repeat the other, is a split, and the split stays real only while that sentence is true.

So separate the candidate content by reach, return a verdict per partition, and name the container before naming the verdict. A body of project conventions came back `do-not-build` as a whole — correctly, for its repo-specific half, which would have become a fourth drifting copy — and shipped as a split instead: the parked gate, the deliberate reds, the lint exclusions and the branch layout went into the repo's missing `CLAUDE.md`, and the rules that outlive the project went into the skill, whose own file states that it deliberately does not repeat what `CLAUDE.md` carries. Which layer a standing rule belongs in is rigwright's placement call; a build verdict needs that call made before it, not after.


## Split or keep — the growth test

Added 2026-09-26, recalculated 2026-09-27 by owner decision (observation #0195), against Anthropic's best-practices page, the Skills overview and the Agent Skills specification (all read 2026-09-27). The default is consolidation: every member adds its name and description to every session's context and one more choice to route among, so fewer members route better and cost less. An audit, a pack design or an upkeep pass proposes a split or a merge only when this test says so, and every such row shows its work.

**Size targets.**

| Part | Target | Ceiling | Source |
|---|---|---|---|
| Body (SKILL.md below the frontmatter) | 2,000–4,000 tokens | 5,000 tokens and 500 lines. Over 5,000 only with a stated reason in the budget row. | Spec: "< 5000 tokens recommended"; overview: "Under 5k tokens"; best practices: "under 500 lines" |
| Description | as short as precise triggering allows | 1,024 characters, hard. At 900 or more it is at the wall for planning. | Spec and best practices; the overview budgets ~100 tokens of metadata per skill |
| Reference files | one file per mutually exclusive context | none, since a file costs nothing until read; a contents list past ~100 lines; one level deep | Best practices; engineering post |
| A reference file that every entry point reads | — | counts as body | Moving it saves nothing |

**1. Shrink in place first, in this order.** Each step is cheaper and safer than the next.
   a. Cut what Claude already knows. For every paragraph ask whether it earns its tokens.
   b. Move deterministic procedure into a bundled script, where the member's profile allows one. Only a script's output enters context. A **standalone** member skips this step for its core job: its profile promises the job completes with no shell or interpreter, so a script there may only be an optional helper that skips cleanly, and the prose steps stay. A **standard** member ships the script inside its own folder and states run-or-read.
   c. Move path-specific material to reference files, one file per entry point or domain, each with a when-to-read pointer.
   d. Tighten the description.
   e. Re-justify the budget row.
Estimate the body after each step. Stop when it is inside the target.

**2. Split only when a wall is hit and the split pays.**
- **Description wall.** After a rewrite, the triggers still cannot fit 1,024 characters. Nothing moves out of a description, so this wall has no in-place fix.
- **Growth wall.** After the whole ladder the body is still over 5,000 tokens, or at 90% or more of its budget row, and the incoming work is concentrated on the part that would move out: more than half of the member's open observations, catalog rows or queued features land on it, or a recorded plan grows it. Room the ladder buys is spent once; steady inflow spends it again.
- **The split pays** only if the part moving out is mostly asked for on its own, with its own trigger words. When both halves load together on most requests, a split costs more than it saves: two bodies, a second description in every session, and a routing seam. Keep the member and ladder harder instead.

**3. Merge when two members behave like one.** Recommend a merge when both hold: the two descriptions compete for the same requests (routing misses are recorded) or the two bodies load together on most requests; and the combined body after the ladder fits 5,000 tokens and the combined description fits 1,024 characters. A merge removes one description from every session.

**4. Otherwise keep, with a trigger.** Record the verdict and the condition that reopens it (description past ~1,000 characters, body past its row or 5,000 tokens, inflow concentrating). Write the trigger into the audit so the next audit checks it rather than re-deriving it.

**5. Cost of a split or merge.** The row names what moves and what stays, the new or removed routing seam, the eval cases and callers that move, and the name-collision check. An auditor's split recommendation is an input; this test decides.

## Security classes

Five classes, scanned on every audit as the security pass (SKILL.md — Entry — Audit) and filed as rows in that entry's one catalog on its P0/P1/P2 severities.

**The pass, in order.** It runs between scoring (Audit step 3) and the catalog (step 5), on every audit. *Stage 1, a scanner, when one is present* *(added 2026-09-28)*: SkillSpector (`--no-llm`, scanning the repo checkout rather than an installed junction), superagent-ai's `skill-security` (`scan.py --format json`), or the `skilltotal` MCP server. Run it, then read its hits by file role and by matched string (Audit application notes below; the matched-string rule is under this section). SkillSpector's JSON nests each hit's file under `issues[].location.file`, and its top-level risk (`CRITICAL` and the like) is an overall score, not a finding: across six audits about 400 HIGH rows validated to zero on direct read, so a catalog row comes from a hit read in its file, never from the headline. When none is present, say "scanner absent" in one line; the pass never waits on one. *Stage 2, the classes below, read by hand every time.* Each finding is a row in the one catalog carrying its class beside its severity (`S-2 · P0-1`), so a security row counts as both; never a separate appendix. A class with no surface is N/A and a pass with no findings is stated in one line. A finding about what an autonomous agent may do at runtime (permissions, cadence, blast radius) is handed to agentwright by name. The prose pass leaves the security pass unrun, since frozen statements can neither introduce nor clear a finding.

All five are properties of the **skill artifact** — how the package is built — never of an agent that later runs it; a finding about runtime permission or blast radius belongs to gatewarden, and cadence to agentwright and is handed there by name. The severities below are floors: raise one where the context is worse, never lower it to keep a catalog short.

- **S-1 injection surface in the instructions.** The skill's own text directs the reader to *act on* what it loads — reference files, fetched pages, file contents, command or tool output, a sibling's handoff — rather than read it. The finding is the missing statement as much as the credulous phrasing: a step that reads anything the skill did not author, carrying no statement that observed content is **data, never instructions**, is the defect. **P0** where such a step exists and the skill has no such statement anywhere; **P1** where the rule is stated but a specific step escapes it. The fix is located, not global — name the step and state the rule at it. The scan also reads what a human reviewer would not: invisible or zero-width unicode, HTML comments carrying directives, base64 blobs, homoglyph domains, and fetch-pipe-shell (`curl … | sh`) patterns in any bundled file — hidden text files here at the same severities, and a fetch-pipe-shell default in generated output is S-4's.
- **S-2 credentials and secrets in the artifact.** A real-looking key, token, password, connection string, session cookie, internal hostname, or private URL anywhere in SKILL.md, a reference file, an example, a fixture, or a filename; or text telling the user to paste a credential into a prompt, a file, or a template slot. **P0** always. Reported by category and location only — the value is quoted nowhere, in the finding, the rewrite, or the report, the same never-echo rule Entry — Port step 3 applies to a sanitize sweep. A placeholder counts as a placeholder only when it cannot be mistaken for live (`<YOUR_API_KEY>`, never a well-formed vendor prefix).
- **S-3 undeclared or ungated capability.** Scanned **against** the universal rule above rather than restating it: diff what the skill's steps assume — tool, script, package, MCP, network, a sibling — against what its frontmatter and docs declare, and file the gap at the severity its declared profile sets. The security half is the second question: a step that deletes, sends, publishes, pays, or is otherwise irreversible, with no gate stated on it. **P0** when the irreversible step is undeclared or ungated; **P1** when it is declared and the gate is only implied. **The contract check** *(added 2026-09-28)* is S-3's third question: does the description claim what the body and any scripts actually do, and nothing they do not? A description that under-states a side effect (the body writes, sends or runs code it never mentions) files here at the severity above; one that over-claims (a job no step performs) is **P1**.
- **S-4 unsafe defaults in generated output.** For a skill that emits artifacts — templates, skeletons, scaffolds, configs, commands — what its shipped default bakes in: blanket or world-writable permissions, verification or checksum disabled, an unpinned dependency or an untrusted source, a secret written into a generated file, a call to a host the skill never names. The default is the finding even where the prose invites the user to change it: a generated artifact ships as written. **P1**, or **P0** where the baked default is itself irreversible or credential-bearing.

- **S-5 personal data, in the artifact and in its repo's history** *(added 2026-09-27, owner rule: "even in history, absolutely no pii")*. Any person-identifying value: a real name, an email address, a phone number, a home or account path (any path through a user's own folder, on Windows, macOS or Linux), an account or machine login name, or a client or employer name the user's naming policy forbids. The scan covers four surfaces, not one: (1) every file in the package; (2) every tracked file in the repo that ships it; (3) the repo's **whole history**, pushed and unpushed (`git log -p --all`, or `git log -G <pattern> --all` per pattern); (4) **commit metadata**: author and committer names and emails on every commit, including merges made in the GitHub web interface, which carry the account's own address unless its email-privacy setting is on. Placeholders (`<name>`, `example.com`, `users.noreply.github.com`) are clean. **P0** always for a public repo, including a hit that exists only in history. The fix for history is a rewrite of the affected range, never a HEAD-only scrub, and a published rewrite is a force-push the user approves. A rewrite does not reach GitHub's pull-request refs or cached views; those need a purge request to GitHub Support, which the finding names. Reported by category and location only; the value is quoted nowhere, the same never-echo rule as S-2. Run it at audit, at the staged-tree leak guard (Packaging step 5), and before every push of a public repo that ships the skill. Scope ends at the skill and the repo that ships it: an estate-wide sweep of every repo, a history cleanup, and the machine's commit and push hook belong to the estate's own security sweep, warden shieldwarden (the engine that sweep calls) and rigwright's hook placement, and are handed there by name.

**Absent is not the same as clean.** A class the audited skill has no surface for is reported N/A rather than scored — structurally inapplicable, the way a skill with no identity surface passes C-2 — and a pass with no findings is stated in one line, never left silent.

**A scanner's finding count is a count of matches, not of problems** *(added 2026-09-13, observation #0060)*. Filtering by file role — the rule Entry — Audit's *Third-party adoption* paragraph states — answers *where* a finding sits, and a verdict needs *what was matched*. So after the role filter, group the surviving findings by the string the scanner actually matched, count the distinct set, and read it: the distinct count is usually one to two orders of magnitude smaller, and a list a person can read in one sitting is the only form in which this evidence gets read at all. One sweep of 21 installed skills returned 690 findings, 109 HIGH and one CRITICAL. Role filtering removed 98 and left 592 in `SKILL.md` and `references/` — the files a model loads as instructions, the highest-value role, the one the rule says to keep and score. Those 592 collapsed to 133 distinct strings, and all 133 were documentation, an API example, or ordinary English: a never-echo rule matched as prompt extraction, a documented API endpoint matched 147 times as exfiltration, text teaching defence *against* injection matched as injection, and the single CRITICAL spanning a line break between the end of one word and the start of the next. Validated findings: zero of 690.

Two consequences ride with it. **A pattern matcher cannot tell describing an attack from performing one**, so the more rigorously a skill documents a threat the worse it scores — a roster where documentation quality tracks risk score is reporting on its own instrument, not on the skills. And **a coverage percentage's denominator is whatever the scanner counted**: one scan's coverage fell from 72.2% to 64.3% when a `.git` directory was removed, because repository furniture had been counted as fully inspected and was padding the denominator. Scope the scan to the skill's own content and re-derive the figure rather than quoting it, and read a category name before trusting its severity — one class filed at HIGH turned out to mean "referenced artifact was not completely inspected", a coverage signal wearing a security name.


## Generator classes

Three classes for a build or audit whose subject **generates one artifact from another** — a manifest from a registry, a doc section from a table, a card from a definition. Scored only where that surface exists; N/A otherwise, on the *Absent is not the same as clean* rule above. What unites them is why they are worth their own classes: all three ship output that **looks complete**, so none of them is visible in the artifact the generator produced — only in a diff against the source.

- **G-1 derive the section list, or fail loudly.** A generator carrying a hardcoded list of its source's sections drifts from that source the moment the source moves. Two real forms: a hardcoded pair of section headings that silently dropped a section from generated output once the source renamed it, and a table parser that returned only the *first* table in a block and silently dropped every later one. Either derive the list from the source, or hard-fail naming the expected section that is missing — never skip-and-continue. **P0** where a skip-and-continue path can drop content with no signal; **P1** where it warns.
- **G-2 a parity mode is part of the generator, not an extra.** Ship a `--check` (or the surface's equivalent): regenerate to a temp location, byte-compare against the committed output, exit non-zero on any drift — and hard-fail rather than warn when an expected input section is absent. Committed build output with no parity gate is indistinguishable from hand-edited output, which leaves the generator's claim to be the source of truth unverifiable. **P1**, or **P0** where the generated artifact is the copy consumers install.
- **G-3 stale-output detection.** A generator notices files in its target directory that it did not just write, and warns or fails on them. Without it a retired artifact stays in place and reads as current truth — the generator's silence is what endorses it.

## Naming-class coverage

A naming convention binds **every class that carries a name**, the classes that feel like infrastructure rather than product included: a scheduled task's or routine's **display name**, its **id**, and a published artifact's **title**. Two rules ride with the id — it carries **no day or cadence suffix**, because the cadence lives in the schedule expression and an id repeating it goes stale on the first reschedule; and it is never the only name scored. Enumerate the classes before scoring any of them: an audit that measured the machine-readable ids, passed green, and never inspected the human-readable display names beside them reported on the half of the surface that was already templated.

## Profiles

**standalone** — the strictest profile. Dependencies: web search only, plus the surface's native file tools for delivery with stated graceful degradation where absent, and — for a packaging or archive-build step only — an optional shell reach (e.g. `zip`) or a stdlib-only interpreter, declared in `compatibility` (Rubric A), that skips cleanly where absent and is never required to complete the skill's core job. No other executable code shipped. Volatile facts isolated in stamped single-update-surface files with a staleness rule (default 60 days). Load budget declared in SKILL.md (≤3 reference loads standard for an audit or a spot task; a full build may legitimately open more where its own doctrine mandates a file every build touches — e.g. a description draft, an incumbent-scan check — each declared in the Load budget by name. **Amended 2026-09-10** (estate findings `skillwright-load-budget-statement-false-and-over-profile`, `skillwright-shell-dependency-beyond-standalone-list`): the cap bounds *undeclared* reach, per the universal rule above — a load a build's own written procedure requires every time is not the drift the cap exists to catch, provided it is named in the Load budget rather than discovered by counting.) Works identically on chat, Code, and API surfaces.

**standard** — tools, scripts, packages, and MCPs allowed, each declared with install/availability notes and per-surface behavior (e.g., "no network on the plain API"). Scripts state run-vs-read. Sibling-skill references allowed under the composition contract: which siblings, and absence behavior (degrade or hard-require) stated in the description or compatibility notes.

**custom** — a pack-defined policy list registered in `pack-registry.md` (e.g., "internal-only: may assume the org's MCP server; must not call public web"). Audits score against the listed policies verbatim. A custom profile that omits the universal rule is invalid.

## Pack conformance checks

A pack may register conformance checks in `pack-registry.md` — pack-charter rules scored on every member audit alongside Rubric A and the declared profile. Standard anchors; a failed check is a P1 finding naming the exact addition. Registered for `foundation` (adopted 2026-07-13):

- **C-1 drift-audit verb** — the skill carries a first-class way to score an existing artifact of its own kind against the standard it implements and report drift *without rewriting it* (a dedicated audit or verification entry, or a stated score-only path).
- **C-2 neutral default** — outputs default to a spec-clean neutral identity; brand and persona voice are strictly opt-in per run. A skill with no identity surface at all passes as structurally N/A.

Checks are pack charter, not universal law: a skill outside the registering pack is never scored against them.

## Audit application notes

Read the audited skill's declared profile first; score against that. Tools on a standard-profile skill are checked for declaration quality, not existence. A skill with no declared profile is scored against Rubric A plus the universal rule only, with a P1 finding to declare one. When the audited skill's pack registers a canonical repo (pack-registry), drift audits also diff the installed copy against that repo's current state and report installed-vs-canonical drift alongside Rubric A; when the repo is unreachable, score rubric-only and say so. When a build request's profile is looser than the skill needs, note once that a standalone-clean build is possible — an offer, not a nag.

**Third-party adoption — three rules** *(moved from the SKILL.md body at 1.6.0, rules unchanged)*. Auditing a skill or plugin someone else maintains, to decide whether to install it, needs three rules the ordinary audit does not. First, **a static scanner's report is evidence, not a verdict** (2026-09-11, observation #0031): record each finding with the role of the file it sits in (runtime command, workflow, hook, eval or test fixture, docs) and score only the runtime set toward the adoption call. Fixture findings are a maintainer-hygiene note, never install risk. Quote the aggregate, then set it aside in one explicit sentence with the reason, or the next reader re-opens the decision on the headline. Second, **group the surviving findings by the matched string, count the distinct set, and read it** (2026-09-13, observation #0060; Security classes above): role says where a finding sits, only the string says what was matched, and a count counts matches, not problems. Re-derive a coverage percentage against the skill's own content rather than quoting it. Third, the audit **says which reading wins**: a verdict recording a scanner score and a direct read side by side, with no rule for reconciling them, is an open decision wearing the shape of a finished one.

**Third-party adoption — the file-role worked case** *(observation #0031)*. One scanner returned 97/100 CRITICAL, DO NOT INSTALL for a plugin whose every HIGH finding sat in its own test harness, while the one runtime file it opened it marked "static parse limit"; a direct read of the runtime files had already found the destructive commands gated behind explicit approval. Read as a number the scan reversed an adoption; read by location it never touched it. The matched-string worked case (592 role-surviving findings, 133 distinct strings) is under Security classes above.

**Usage evidence — probe capability before a zero decides anything** *(added 2026-09-13, observation #0055)*. A zero-invocation count has three candidate causes the number itself cannot separate: the skill was never needed, nobody reached for it, or it could not have fired on the material in front of it. One cheap probe separates them — take a real artifact from the counted window, run the skill or its detector over it, and record what came back. Output of any kind leaves the keep/drop question standing. Nothing at all makes it a capability or usage-rule finding instead: one adopted skill's detector could not parse `.astro` and did not read standalone `.css`, so 60 days of silence over a 70-file `.astro` project was structural rather than a discipline problem, and the fix was a parser plus a rule to run it against built output rather than source — an answer no keep/drop verdict would have produced. Record the probe's result beside the count so the next reviewer inherits evidence rather than an inference, and re-probe every sibling flagged on the same reasoning: the untested inference had already been reused against a second member before anyone checked it. Where the environment cannot run the probe, report it as owed and hold the keep/drop call rather than settling it on the count. How the count itself is read — which counter, what it cannot see, and the three states a zero can mean — is rigwright's Entry — Audit usage-evidence rule; this is the prior question of whether zero was ever possible.

## Current platform — the currency check

Scored on every audit, of this pack's skills or anyone's (owner decisions 2026-09-30). The check reads the live docs on the day (the models overview, the Claude Code docs, the Agent Skills and plugin docs), never a remembered list. Three dimensions, standard anchors, each finding a catalog row:

- **Models.** Work routes to a sensible tier with a sensible effort per task; no retired model, no stale default, no workaround only an older model needed. Bodies, descriptions and design docs name roles (the top tier, the default worker, the fast tier) or family aliases (opus, sonnet, haiku), never a version. Exact ids live in **one** dated reference file per skill, with a `Last verified:` stamp and the `refresh` entry that re-verifies it; every other file points there. Evals assert behaviour (picks the top tier for a design task), never a model string. Run records (ledgers, RESULTS run-with lines, CHANGELOG lines) state the exact id used; they are history, not guidance, and are exempt.
- **Features.** The skill uses current Claude features where they fit: effort levels, subagents and the Workflow tool, hooks, artifacts and design systems, Docs, Research. A hand-rolled step a native feature now does is a finding. Bodies prefer capability words ("the platform's subagent tool") to feature names that churn, with a pointer to the live docs.
- **Layout.** Frontmatter fields, references on demand, body size, `plugin.json` and marketplace shape match the current Agent Skills and plugin docs.

**The mechanical sweep.** Outside the one allowed dated file and the run records, grep every file for a model family followed by a number (`(Opus|Sonnet|Haiku|Fable|Mythos)[ -]?\d`, `claude-[a-z]+-\d`) and for dated feature claims ("as of <date>", "new in <version>"). Each hit is a P1 row. A stale allowed file is a refresh through its own verb, not a rewrite.

**When the platform changes, the skills follow.** A new model, feature or layout rule (seen by a model watch, a model-table refresh in another skill, or a platform sweep) triggers a currency sweep of every skill: this section is updated first, so the next audit checks the new rule, then each skill is audited against it. Fixes land as patch bumps; a release freeze, while one is in force, holds them until it lifts.

## Audit catalog rows — evidence rules

Every catalog row (Audit step 5, a security row, an upkeep finding) meets these, and the audit's self-check confirms each before the gate:

- **Quote the capability.** A row that says a tool, CLI or command can or cannot do something quotes the tool line, the `--help` output or the doc sentence that shows it, with its source. Without a quote the row is marked `unverified` and cannot be P0 (#0209).
- **Volatile classes are closed.** The legal `volatile.json` classes are `calendar` (needs `cadence_days` and a dated `Last verified: YYYY-MM-DD` stamp in the file's first lines, or under the named section's heading when the pointer is `file.md#anchor`) and `event-driven` (no cadence). A plan or row with any other class fails the self-check; an anchor whose heading does not exist is P1 (#0215, #0221).
- **Anchor sweep around a slim.** Before any slim or move of text, list each eval case's anchor rule (the body sentence an assert depends on) and each routing-seam row's deciding phrase; after the edit, confirm both still exist word for word, or record where they moved. Every audit runs the same sweep (#0224).
- **Rejected rows carry a reopen condition.** A row the user rejects or defers keeps one line naming what reopens it (a count past a number, a sibling shipping, a platform change). A later policy change greps past catalogs for its own name and reopens what matches (#0228).
- **Registry numbers are checked, not trusted.** A stated member count or budget row is compared with the roster and the measured bodies (`build.py --check` in the source repo), and a retired name or phrase on a live surface is a P1 row (#0227).
- **Name the usage counter.** A usage count names its source and that source's blind spot. Claude Code's `/skill-doctor` report is the first usage-count source for an installed skill; transcripts are the second (P2-4).

## Prose pass

How a skill's or pack's **own files** read (SKILL.md, README, CHANGELOG, SOURCES, reference docs, CLAUDE.md, spec files), asked for as humanize, tighten, or fix the writing *(moved from the SKILL.md body at 1.6.0, procedure unchanged)*. It replaces Audit steps 2 to 4 (a register ask needs no incumbent scan and no parity verdict) and keeps steps 1 and 5 to 7. Counting unit: the **statement**, one sentence or cell carrying a rule, fact, threshold, count, path, or command.

1. **Scope and freeze.** Name the files in scope at their repo paths and inventory their statements. Statements are frozen: an edit that changes what a rule says, drops its counting unit, or moves a threshold has changed the skill, and that is a Build or Audit rewrite with its own gate. Text written to an audience through a channel is out of scope at every path (a release announcement, a post, an email); that is commscribe's, handed back by name rather than edited, and so is docs prose outside a skill package (a project's docs, a Claude Docs page).
2. **Read for the four register defects this skill already scores**, per file, with line references: CAPS imperatives and MUST/NEVER outside genuinely fragile steps (Rubric A — instruction style) · padding, a heading or file carrying no statement its reader needs (SKILL.md Behavior notes — Never pad) · one statement made twice, so neither copy is authoritative (Rubric A — progressive disclosure) · rot, a time-sensitive fact outside a stamped volatile file (Rubric A — no rot).
3. **Rewrite claim-preserving, then catalog per Audit steps 5 to 7.** Re-inventory the rewrite and diff it against step 1's list before showing anything: same statements, same units, same numbers, nothing the source did not carry. A changed inventory is a failed pass, fixed rather than filed; register findings are P2 and a drifted statement is never one of them.
