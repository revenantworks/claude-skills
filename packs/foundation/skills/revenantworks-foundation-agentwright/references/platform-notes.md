## Enforcement surfaces by platform

**Claude Code / Claude Agent SDK** — three deterministic gates, layered: (1) **permissions** — allow/ask/deny rules per tool — "Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order"; six permission modes (`default`, labelled Manual, with `manual` as an alias; acceptEdits, plan, auto — "a background classifier checks that they align with your request" — dontAsk, bypassPermissions); `permissions.disableAutoMode` or `disableBypassPermissionsMode` set to `"disable"` turns a mode off *(raw `permissions.md`, 2026-10-01)*; org-wide managed settings that can pin rules, hooks, and MCP servers to the managed layer alone (`allowManagedPermissionRulesOnly`, `allowManagedHooksOnly`, `strictPluginOnlyCustomization`) *(2026-09-28)*. "With Claude Code v2.1.283 or later, auto mode is the built-in starting permission mode for interactive terminal and VS Code sessions", and in auto mode "Your explicit ask and deny rules still apply" *(permission-modes and security pages, 2026-10-01)* — so an unconfigured interactive session is now classifier-reviewed, not human-reviewed. (2) **sandboxing** — "the operating system enforces that boundary for every Bash, PowerShell, or Monitor command and its child processes", with domain allow/deny lists; it "runs on macOS, Linux, and WSL2. Native Windows is not supported. On Windows, run Claude Code inside a WSL2 distribution" *(raw `sandboxing.md`, 2026-10-01)*; "sandbox restrictions still apply even if a prompt injection bypasses Claude's decision-making" *(raw `permissions.md`, 2026-10-01)*. (3) **hooks** — 33 lifecycle events *(re-counted 2026-10-01)*, 5 handler types (command, http, mcp_tool, prompt, agent); PreToolUse receives the full tool call and can deny with a reason fed back to the model, force a prompt, rewrite the input, or let it proceed — "The hook can deny the call, but staying silent doesn't approve it"; PostToolUse closes the loop. Hooks are deterministic (they don't ask the model). **Hook decisions never bypass permission rules**: "PreToolUse hook decisions don't bypass permission rules. Claude Code evaluates deny and ask rules regardless of what a PreToolUse hook returns", and "A blocking hook also takes precedence over allow rules" (exit 2 stops the call before the rules are evaluated). One exception on the same page: a plugin **mod** that hooks `tool.check` "answers after the rules and the `PreToolUse` hooks have decided, and its answer can replace theirs" — it can approve a call a non-managed `PreToolUse` hook blocked, so an installed mod is part of the enforcement layer an audit reads *(raw `permissions.md`, 2026-10-01)*. `disableAllHooks` "set in user, project, or local settings can't disable those managed hooks" *(2026-10-01)*. But hooks are also an attack surface: 2026 CVEs turned repo-supplied hooks into an RCE vector (a malicious `settings.json` executing on load — CVE-2025-59536 / CVE-2026-21852; npm and PyPI worms planting SessionStart hooks, still active 2026-08) *(carried, not re-verified)*. On trust, per the docs: "A `-p` session shows neither prompt" (the workspace-trust dialog and the `.mcp.json` approval); frontmatter hooks in a project skill register "when you or Claude invoke the skill, including in a `-p` run in a folder you haven't trusted", while a project subagent's frontmatter hooks wait for trust and "A `-p` session doesn't count as accepting it" *(2026-10-01)*. Treat any hook you didn't write as untrusted code; pin versions; open an unfamiliar repo with `--bare` or `--settings '{"disableAllHooks": true}'`. A scheduled `/loop` fire "only runs skills that Claude is allowed to invoke on its own": a skill marked `disable-model-invocation: true`, one withheld by `skillOverrides` or a `Skill` deny rule, a built-in command and an MCP prompt "reach Claude as plain text instead of executing" *(2026-10-01)* — a spec whose prompt is a skill name confirms the skill is model-invocable, or the run silently does nothing.

**Claude Code plugins** — a plugin can carry parts that act without a fresh prompt, and an inventory or audit must list them beside hooks: **monitors** (`experimental.monitors`, default `monitors/monitors.json`) — "Shell command Claude Code runs as a persistent background process in the session working directory", started at session start or "the first time that skill runs" (`when: "on-skill-invoke:<skill>"`); "Monitors run only in interactive sessions, and not on Amazon Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry", and a monitor command cannot read `${user_config.*}`. **Channels** bind a message channel ("such as a bridge to a chat app") to one of the plugin's MCP servers, so inbound messages are untrusted input. A **skill with `context: fork`** runs "in isolation": Claude Code "starts a new subagent of the type set in the `agent` field"; `user-invocable: false` hides a skill from the `/` menu so only Claude invokes it. A plugin's `settings` may set the default `agent` ("Only `agent` and `subagentStatusLine` take effect"). A plugin-root `CLAUDE.md` is not loaded. **Executables:** files in a plugin's `bin/` "are on the Bash tool's `PATH` while the plugin is enabled, so Claude runs them as bare commands", and "claude.ai and Cowork don't install a plugin that has this directory"; LSP servers and workflows are further components an inventory lists. Mods: the manifest's `types` field "declares the `$.state` values and `$` nouns of a mod"; the mods reference itself was seen and not read. *(verified 2026-10-01, code.claude.com/docs/en/plugins-reference and /skills, raw `.md` pages)*

**claude.ai / Cowork** — scheduled tasks ("hourly, daily, weekly, on weekdays, or manually") that "run remotely, so they run on their cadence even when your computer is asleep or the Claude Desktop app is closed" — but "If a scheduled task requires local files or apps, it will only run locally"; each has an approval mode set at creation; "Scheduled tasks have access to the same capabilities as regular Cowork tasks, including connected tools, skills, and installed plugins"; pause, resume and delete. No hook layer — the article names none, so guardrails live in the task prompt plus the platform's own action confirmations. *(verified 2026-10-01, support.claude.com article 13854387)*

**MCP (any host)** — approved-server allowlists are the control (`allowedMcpServers` / `deniedMcpServers`, which also "filter the delivered connectors"); real CVEs in popular servers (three in mcp-server-git, disclosed 2026-01-20, chainable to RCE through a prompt injection) *(2026-08-17, not re-verified)* make "which servers, pinned how" a protected-resource decision, not a convenience one. The docs: "Servers that fetch external content can expose you to prompt injection risk", and Anthropic reviews directory connectors "but does not security-audit or manage any MCP server". Tool descriptions are untrusted input to the host. **Project servers in unattended runs:** "In `claude -p` runs, Agent SDK sessions, and cloud sessions, Claude Code can't show that prompt: it loads project-scoped servers without asking" — a committed `.mcp.json` is live in every routine and headless run. Two per-call gates reach a person: "MCP tools marked `requiresUserInteraction` prompt on every call and don't offer an always-allow option" (desktop page), and an organization connector tool set to `ask` "prompts on every call … even in `acceptEdits`, `auto`, and `bypassPermissions` permission modes, and never offers an option to remember your choice" — on an unattended surface both are stalls. *(verified 2026-10-01, code.claude.com mcp, security and desktop-scheduled-tasks pages)*

**Framework agents (LangChain, CrewAI, ADK and similar)** — no platform permission layer of their own. The hard tier can come from **Microsoft Agent Governance Toolkit** (MIT, 2026-04-02): a stateless policy engine that intercepts every action before it runs, execution rings, and an emergency kill switch; it integrates ten frameworks. An emit or spec for such an agent can then write "carried by the policy engine" in the gap table instead of "prompt only". *(verified 2026-09-26 against opensource.microsoft.com)*

## Scheduling / cadence surfaces

Native schedulers: Cowork scheduled tasks (hourly / daily / weekly / weekdays / manual; remote by default) and Claude Code desktop tasks (Manual / Hourly / Daily / Weekdays / Weekly presets, custom cron or a one-time run by asking, 1-minute floor; created in the Desktop **Code** tab under **Routines → New routine → Local**, where **Cloud** creates a routine instead); Claude Code cloud routines (schedule with a 1-hour floor, one-off, API, or GitHub event, combinable; Anthropic-managed or an organization's self-hosted environment); the session-scoped `/loop` (1-minute floor, fires only while the session runs and is idle, recurring tasks "automatically expire 7 days after creation", up to 50 per session, restored on `--resume` except a self-paced loop; `CLAUDE_CODE_DISABLE_CRON=1` turns the scheduler off — a polling aid, not an unattended surface) *(verified 2026-10-01, routines, desktop-scheduled-tasks and scheduled-tasks pages)*; CI cron (GitHub Actions et al., 5-minute floor) for repo-anchored agents; the Agents SDK runs on any external scheduler. Full per-target fields, gates, and missed-run behavior are in **Emit targets** below — single-homed there, not restated here. The checklist's cadence decision maps to whichever of these the agent lives on. A cadence the platform can't express (e.g. "every 61 days" on Cowork) becomes a nearest-cadence run plus an in-run date check.

**Kill-switch verify — one check per target** (added 2026-10-01, audit P2-6). The drill in SKILL.md *Entry — Design* ends on evidence, never on the stop command's success. Each emit names the one read that proves the hard layer held, then the same proof for every target: no new run, artefact or commit after the next due fire time.

| Target | Verify read after the stop |
|---|---|
| Claude Code routine | `/schedule list` shows the routine paused or gone; the routine's run history shows no fire after the next due time |
| Claude Code desktop task | the task's Status toggle reads Paused on its detail page in the Routines list; its history lists no run after the next due time |
| Cowork scheduled task | the task reads paused in the scheduled-task list; no new output at its destination after the next due time |
| CI cron | `gh workflow list --all` shows the workflow's state as disabled; `gh run list --workflow <file> --all` (the flag reaches a disabled workflow's runs) shows no run after the next cron time |
| Workflow runner | the runner's own workflow list shows it inactive; the revoked connection fails its test call |

**The thin-target finding, and why emit states a gap rather than a spec.** A target with no permission model, no tool-grant scope and no isolation layer — a workflow runner whose gates nobody built, or any surface whose kill switch is only pause or deletion — is *prompt plus cadence*. Control areas cannot be enforced there; at most they can be *described* to a model that may or may not comply, which is the same probabilistic footing the checklist exists to avoid. An emit to such a target says so in plain terms, keeps the controls that survive as prompt-level instructions, and names the ones that do not survive at all. Where the spec's blast-radius decision depends on a control the target cannot hold, the honest emit is that the surface is wrong for this agent — SKILL.md *Entry — Emit* carries that as a Restraint condition in the paragraph after step 6.

**Missed-run semantics differ per target and change what a prompt must say.** Claude Code desktop checks on wake for runs missed in the last seven days and starts **exactly one** catch-up for the most recently missed time, discarding older ones; a run skipped because the machine slept, the prior run was still going, or other tasks were running is listed in the task's history with its reason; "If your computer sleeps through a scheduled time, the run is skipped" until that one catch-up. So a 9am task can fire at 11pm, and a spec that cares about timing puts its own clock check in the instruction. Cowork scheduled tasks run remotely by default and no longer depend on the machine; a task that must run locally still does, and the support article states no catch-up rule for it (re-read 2026-10-01). Cloud routines do not depend on the user's machine, but a cloud routine whose GitHub connection is missing or expired **skips its runs for up to 72 hours**, then turns itself off until GitHub is reconnected and the routine is re-enabled — a spec for a repo-reading routine says who notices the skip. Limits split by kind *(2026-10-01; the earlier "daily cap" is gone from the page)*: a scheduled run over the account's 100-per-hour limit **waits** until the limit resets; Run now and API fires over their limits **fail**; GitHub events past the hourly caps are **dropped**; a run that hits the subscription usage limit is **rejected**, not queued, unless usage credits are on; while the subscription is paused, routines are on hold. A routine run's green status means the session exited without an infrastructure error, not that the task succeeded — the transcript is the only evidence, which is what the zero-signal line is for. Every emitted schedule states which of these applies; it is the field no scheduler's own form asks for.

**Cloud routine facts an emit and an audit rely on** *(verified 2026-10-01 against the raw routines page, except where marked)*. `/schedule` (alias `/routines`) creates, lists (`/schedule list`), updates and runs routines from the CLI; it needs a claude.ai subscription login and is unavailable inside a cloud session; adding an API trigger is web-only, and the CLI can add a GitHub trigger from v2.1.225. Since v2.1.227 `/schedule` also reads a run's log to explain "tool errors, permission denials, and the final result", so it is the surface that reaches a routine's history. Each run is also given a platform **session branch** and a **stop hook** that demands that branch be pushed *(observed in one run log 2026-09-21, observation #0122; still absent from the raw routines page 2026-10-01 — the nearest vendor line is the security page's "Git push operations are restricted to the current working branch" for cloud sessions)*; a routine that works on its own branch cuts it before its first commit, or every run reports a disagreement between the two schemes.

**Stagger.** Anthropic-managed schedulers start a run a few minutes after the nominal time, deterministically — the same task or routine always takes the same offset. A routine scheduled "exactly on the hour, such as 9:00, it can start several minutes late", so the docs advise a few minutes past (9:07). The session-scoped `/loop` adds up to 30 minutes for hourly-or-slower recurring tasks ("or up to half the interval" for faster ones), and a one-shot set for the top or bottom of the hour fires "up to 90 seconds early" *(2026-10-01)*. Specs that key on exact wall-clock boundaries are written against the *date*, not the minute.

**Creation path decides what a scheduled job can be given later** *(observed 2026-09-12 in use, not vendor-documented — confirm on the next refresh)*. A job created as a Cowork task carries no `sources` field, so a repo read cannot be attached to it afterwards; getting one means recreating the job on the API-created routine path, which is a different object with a different home, not a setting. So a fix whose only mechanism is "attach a real source" is a creation-type change, and emit raises it as the step 1 boundary question rather than performing it: the surface an unattended agent was created on is rarely changeable in place, and the change is the user's to make.


## Kill-switch & governance state

A real kill-switch is **layered**, not one button: session termination → permission revocation → circuit breakers → rollback → full deactivation, with depth scaled to the agent's autonomy. The Five Eyes joint guidance *Careful Adoption of Agentic AI Services* (CISA and the Australian Signals Directorate's ACSC with US and international partners; the CISA resource page is dated "May 01, 2026", re-read 2026-10-01 — the full text sits on cyber.gov.au and was not re-read) tells operators to assume unexpected behavior, grant minimum access, design for containment and reversibility, and keep the ability to intervene and deactivate once running *(verified 2026-08-17)*; EU and Singapore frameworks treat deactivation ability as a core requirement *(carried from the 2026-07-23 pass, not re-verified)*. The gap is real: only ~21% of enterprises report mature agent governance, and more than a third admit they could not shut down a rogue agent today *(industry-survey figures from the 2026-07-23 build-time research pass — vendor/analyst-reported, directional not audited)* — the reason the checklist makes kill-switch layers a first-class area rather than an ops afterthought.

## Injection state of the art

Prompt injection remains **unsolved** — current best practice is blast-radius limitation, not prevention: sandbox so a successful injection hits hard limits; deterministic hooks/guardrails on the actions that matter; untrusted content quarantined per the trust-tier rule. Claude Code's own docs now say the same in their own words: "Settings rules are enforced by the client regardless of what Claude decides to do. CLAUDE.md instructions shape Claude's behavior but are not a hard enforcement layer" *(memory page, 2026-10-01)*, and the sandbox holds when an injection has already turned the model *(2026-09-28)*. One platform default narrows the injection path on reads: "For most fetches, WebFetch runs a separate model call over the page, and Claude receives that call's answer instead of the raw page" *(security page, 2026-10-01)* — a mitigation, not a boundary, since the answer can still carry injected text. The same page's own caveat: "no system is completely immune to all attacks". Two field notes worth carrying into specs: agent-authored commits leak credentials at roughly twice the human baseline (secret-blocking rules earn their keep) *(carried from the 2026-07-23 pass, not re-verified)*, and the guardrail mechanism itself is part of the attack surface (see the hook CVEs above) — audit the enforcement layer like any other dependency.

## Checklist-area → platform-mechanism map

| Checklist area | Current mechanism (by platform) |
|---|---|
| Hard guardrails | Claude Code and Agent SDK deny rules (deny-first, not bypassable by a hook) + hooks + sandbox · Agent Governance Toolkit policy engine for framework agents |
| Soft guardrails / HITL | ask-rules + approval prompts (attended sessions only — `design-checklist.md` area 2) · MCP `requiresUserInteraction` and an org connector `ask` policy (prompt every call, no remember) |
| Kill-switch layers | permission revocation, sandbox teardown, scheduler pause or disable (`CLAUDE_CODE_DISABLE_CRON=1` for session `/loop` tasks), token revocation, the org Routines toggle, the Agent Governance Toolkit kill switch — layered per above |
| Protected resources | sandbox scopes, domain allowlists, MCP server allowlists, routine environment allowlists, routine branch-push checks |
| Cadence | Cowork + desktop native cadences · cloud routines (1h floor, one-off, API, GitHub events) · CI cron · external schedulers |
| Injection hygiene | sandbox blast-radius limits + trust tiers; hooks as deterministic filters; the routine fire-payload wrapper |
| Output contracts / handoffs | schema validation at the boundary |

The seven rows above cover areas 1–6 and 9 — guardrail tiers (2) spans two rows, and output contracts (6) shares one with handoff schemas (5).

Three areas have no row. **Zero-signal (7)** and **failure & retry (8)** are decided by `design-checklist.md` and the SKILL body; no platform mechanism implements them. **Trust tiers (10)** has no row of its own because its enforcement is the mechanisms already listed above — read-only permission modes, tool allow/deny rules, approved-server allowlists (*Enforcement surfaces*), and schema validation at the boundary (*Output contracts / handoffs*) — and the injection-hygiene row names trust tiers outright. Blast radius is the pre-checklist sizing step (SKILL.md *Turn shape 3*), not one of the ten areas.
